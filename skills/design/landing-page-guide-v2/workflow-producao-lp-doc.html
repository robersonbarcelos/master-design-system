01 · Visão Geral

O que esse workflow faz

Toda vez que Diego (ou alguém do time) diz "quero produzir uma página", esse workflow é acionado. Ele define a sequência exata de passos, quais skills usar em cada etapa, onde o Claude deve parar e esperar aprovação humana, e o que valida que a página está pronta para ir ao ar.

🔑
Regra mais importante

Nenhum código é escrito antes da aprovação do Gate 3. Brief + direção estética + narrativa precisam estar aprovados por Diego antes de qualquer implementação.

🎯

Objetivo

Produzir LPs que convertem visitantes, se diferenciam visualmente, e chegam a PageSpeed Mobile ≥ 85 consistentemente.

👥

Quem usa

Diego aciona o workflow. Claude orquestra as skills. O humano aprova em 5 gates. A entrega é uma LP em produção, auditada e com score documentado.

🗂️

Onde vivem os arquivos

SKILLS/Master-social-design-system/skills/design/landing-page-guide-v2/ — workflow, referências de copy, catálogo de narrativas.

⚡

Stack suportada

HTML puro + CSS custom properties + Vanilla JS (mentoria, DeFi). React/Next.js (intushub-template). Escolhido no Gate 1.

03 · Fluxo Ponta a Ponta

6 Etapas · 5 Gates

Cada etapa tem um entregável claro. Cada gate tem um critério explícito de bloqueio. Sem aprovação → não avança.

1

Briefing Completo

Conversa direta com Diego. Coleta: produto, público, tipo de página (vendas ou serviço), tom, stack, mínimo 3 referências visuais, anti-objetivos e conteúdo disponível (imagens, vídeo, copy, depoimentos).

Humano decide Nenhuma skill acionada
🔒

Gate 1 — Briefing validado

Bloqueia se: tipo de página não definido, menos de 3 referências visuais, sem anti-objetivos declarados.

Gate obrigatório Aprovação: Diego
2

Análise Competitiva

Claude abre cada referência no Chrome. Mapeia IA/UX patterns, estrutura de seções, copy approach, CTAs. Identifica o que todos fazem igual (table stakes) e o gap de diferenciação. Produz tabela comparativa.

competitive-analysis Chrome extension LLM analisa
🔒

Gate 2 — Oportunidade de diferenciação aprovada

Bloqueia se: Diego não confirma qual padrão competitivo adotar ou rejeitar. Sem direção clara → revisitar referências.

Gate obrigatório Aprovação: Diego
3

Direção Estética + Design System + Narrativa

3A — Direção estética via impeccable → shape: nomeia a direção (Minimalista Refinado / Bold / Editorial / Retro-Futurista), define scene sentence, color strategy, tipografia, motion strategy, layout approach.

3B — Estrutura de seções via catalogo-narrativa-lp.md: sequência de seções aprovada por tipo (Vendas PAS ou Serviço/Mentoria).

3C — Copy framework via copy-conversao-lp.md: headlines sem travessão, sem cara de IA, CTAs com verbo+resultado.

impeccable → shape catalogo-narrativa-lp copy-conversao-lp LLM propõe Diego aprova
🔒

Gate 3 — O GATE MAIS CRÍTICO

Diego aprova: brief visual escrito, direção estética nomeada, sequência de seções, headlines principais. Nenhuma linha de código antes desse gate.

Gate CRÍTICO Aprovação explícita: Diego
4

Prototipação de Seções Complexas

Apenas para heroes com motion design, animações não-triviais ou elementos visuais experimentais. Claude gera 3 variações HTML, abre no Chrome, Diego escolhe 1 direção ou hibridiza 2.

Se não há seções complexas, Gate 4 é pulado — avançar direto para Etapa 5.

huashu-design Chrome extension Diego escolhe variação
🔒

Gate 4 — Protótipo visual da hero aprovado

Bloqueia se: Diego não aprovou qual variação seguir. Pulado se não há seções complexas.

Gate obrigatório Aprovação: Diego
5

Implementação

Código fiel ao brief aprovado. Design system como CSS custom properties no :root antes de qualquer componente. Seguir os 11 elementos essenciais (11-essential-elements.md). Fontes self-hosted em woff2. Imagens em webp. Reveal on scroll via IntersectionObserver.

landing-page-guide-v2 11-essential-elements LLM implementa preview no Chrome
🔒

Gate 5 — Preview no Chrome confirmado

Bloqueia se: sem screenshot seção a seção, sem verificação de erros de console. Sem esse gate → não entra na auditoria.

Gate obrigatório Chrome extension
6

Auditoria + Polish + PageSpeed

1. critique-screen → 4 dimensões (hierarquia, brand, composição, tipografia).

2. impeccable → clarify → copy sem cara de IA, sem travessão, sem jargão.

3. impeccable → polish → micro-detalhes finais.

4. impeccable → audit → a11y, responsivo, anti-patterns (score 0-20).

5. pagespeed-audit → URL de produção real, scores Mobile + Desktop, correções antes/depois documentadas.

05 · Regras de Copy

Permanentes em todas as páginas

Derivadas de references/copy-conversao-lp.md. Valem para 100% das LPs, sem exceção.

❌ Nunca usar

  • → Travessão (—) em qualquer posição — substituir por ":" ou reescrever
  • → "Não X, é Y" — fórmula saturada de copy IA
  • → "Enquanto X, você Y" — genérico, poderia ser qualquer produto
  • → "Destranca", "potencializa", "revoluciona" — jargão vazio
  • → "Saiba mais", "Enviar", "Clique aqui" — CTAs fracos
  • → Urgência falsa ou contagem regressiva falsa
  • → Depoimento sem nome, foto ou número real

✅ Como escrever

  • → Frase curta antes de frase longa — cria ritmo
  • → Começar com o problema concreto, não com a empresa
  • → Números específicos: "70% menos tempo" > "muito mais rápido"
  • → CTA = verbo + resultado: "Quero meu diagnóstico"
  • → Voz ativa, verbo no início da frase
  • → Contrações PT-BR: "pro time", "pra você", "a gente"
  • → 1 ideia por seção, sem mistura de mensagens
⚠️
Teste rápido antes de publicar

Leia cada frase e pergunte: "essa frase poderia ter sido gerada por qualquer IA para qualquer produto?" Se sim, reescrever com dado específico do Diego ou do cliente real.

Métricas alvo e protocolo

Roda na Etapa 6, após deploy em URL de produção real. Nunca em localhost — CDN, DNS e servidor afetam o resultado.

Correções de maior impacto

  • → fetchpriority="high" + loading="eager" na imagem hero — reduz LCP
  • → Fontes self-hosted woff2 (não Google Fonts externo) — reduz TBT
  • → Scripts de terceiros com defer — reduz TBT
  • → width e height em todas as imagens — zera CLS
  • → loading="lazy" em tudo abaixo da dobra — reduz payload inicial

O que NÃO fazer (aprendizados reais)

  • → requestIdleCallback para fontes — causa CLS visível
  • → rel="preload" na hero img — pode piorar LCP
  • → Minificação CSS no Cloudflare — quebra @font-face e CSS vars
  • → Self-host de GTM/scripts de terceiros — viola ToS
  • → Testar no localhost — resultado não reflete produção
🚫
Critério de bloqueio de publicação

Score Mobile Performance < 85 bloqueia a aprovação final. A LP não é declarada pronta até esse critério ser atingido. Atacar as top 3 oportunidades do relatório antes de qualquer outra coisa.

07 · Fragilidades e Riscos

O que pode dar errado

⚠️

Pular o Gate 3

O risco mais alto. Se o Claude começar a codificar sem aprovação explícita do brief + direção estética, todo o trabalho pode precisar ser refeito. Gate 3 é inegociável.

🎭

Copy com cara de IA

LLM tende a gerar frases que soam genéricas. O checklist do copy-conversao-lp.md e o comando impeccable → clarify existem exatamente para isso.

🌑

Contraste insuficiente

Cards sobre fundo escuro com diferença de luminosidade < 10 pontos ficam invisíveis. Mensurar com DevTools antes do Gate 5.

🖼️

Imagens sem dimensões

Cada imagem sem width e height gera layout shift (CLS). Causa direta de score baixo no PageSpeed Mobile.

🔤

Fontes externas bloqueando

Google Fonts via CDN adiciona round-trip externo. Sempre migrar para self-hosted woff2 antes do Gate 5 para não descobrir o problema no PageSpeed.

📱

Testar só no desktop

Google indexa mobile-first. PageSpeed Mobile é o score que importa. Verificar no Chrome com viewport 375px antes de qualquer aprovação final.

💡
Dívida técnica conhecida

O workflow de auditoria (critique-screen) não tem uma skill standalone para performance de produção — o protocolo pagespeed é manual (abrir a URL, ler, agir). Uma automação via PageSpeed Insights API eliminaria o passo manual.

08 · Como Reaproveitar

Esse padrão em outros workflows

A estrutura de Gates + Skills mapeadas pode ser aplicada a qualquer processo de produção de conteúdo ou artefato digital no ecossistema INTUS HUB.

🎨 Carrossel de redes sociais

Gate 1: tema + referência + voz. Gate 2: roteiro aprovado. Gate 3: JSON de slides aprovado. Skills: carrossel-intus + critique-screen.

📧 Newsletter

Gate 1: pauta + ângulo. Gate 2: estrutura de seções aprovada. Gate 3: copy final aprovado. 5 imagens obrigatórias (img1-4 corpo + img5 CTA exclusivo).

🎥 VSL / Script de vídeo

Gate 1: objetivo + persona + duração. Gate 2: estrutura PAS aprovada. Gate 3: roteiro word-by-word aprovado. Gate 4: gravação.

🤖 Automação / Skill nova

Gate 1: o que faz, quem usa, qual trigger. Gate 2: arquitetura aprovada. Gate 3: pseudocódigo aprovado. Gate 4: implementação + teste. Gate 5: documentação HTML.

✅
O padrão que funciona

Qualquer produção que envolve LLM + aprovação humana pode usar essa estrutura: Trigger → Coleta → Gate humano → Proposta LLM → Gate humano → Execução → Gate técnico → Auditoria. Os gates impedem que o LLM avance na direção errada por muito tempo.

09 · Checklist de Publicação

A página está pronta quando

Design e copy

Direção estética nomeada e executada consistentemente
Nenhum travessão (—) em todo o copy
CTAs com verbo + resultado (não "Enviar")
Variação de fundo entre seções (quebra visual)
Cards com contraste distinguível do fundo
Prova social com nome, número e contexto real
Formulário multi-step com progress indicator

Técnico e performance

Score Mobile PageSpeed ≥ 85
LCP < 2.5s (hero img com fetchpriority="high")
CLS < 0.1 (width + height em todas as imagens)
Fontes self-hosted woff2 (sem Google Fonts externo)
Scripts de terceiros com defer
Sem erros de console
Scores antes/depois documentados

Esse workflow existe para garantir que nenhum código seja escrito antes que Diego aprove a direção, nenhuma página vá ao ar sem PageSpeed Mobile ≥ 85, e nenhuma linha de copy passe sem ser testada contra a pergunta: "isso poderia ter saído de qualquer IA para qualquer produto?"
